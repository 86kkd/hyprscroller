# 注释规范 (Commenting Guidelines)

本仓库的注释目标不是“给已经熟悉代码的人补提示”，而是让第一次读
`layout / lane / stack / overview` 链路的开发者也能在较短时间内建立心智模型。

## 基本原则

1. 先解释职责，再解释细节

- 复杂 `.cpp` 文件必须有 `@file / @brief`
- 文件头应说明这个文件在整体调用链中的位置
- 对关键文件建议补一段“推荐阅读顺序”

2. 注释优先解释“为什么”，不要只解释“做了什么”

- 好注释：为什么这里要先删空 lane 再切焦点
- 弱注释：删除 lane

3. 复杂流程必须有块状注释

以下情况默认应该补块状说明：

- 状态机切换
- 跨 monitor / 跨 workspace handoff
- payload 提取与恢复
- 坐标系变换
- OpenGL / render state 暂存与恢复

4. 纯逻辑和副作用要明确区分

- 纯 routing / planning helper：解释输入布尔条件和输出决策
- 运行态 helper：解释会修改哪些外部状态、为什么顺序重要

## 建议写法

### 文件头

```cpp
/**
 * @file ...
 * @brief ...
 *
 * 这个文件在整体链路中的位置
 * 主要输入 / 输出
 * 推荐阅读顺序（如果需要）
 */
```

### 函数前块注释

适合解释一整个流程函数：

```cpp
// 这个函数解决什么问题。
// 进入时依赖哪些状态。
// 返回或副作用是什么。
```

### 关键逻辑块注释

适合解释一个分支或一段顺序要求很强的逻辑：

```cpp
// Phase 1: ...
// 这里必须先做 A，再做 B，否则 ...
```

## 应避免的注释

- “给变量赋值”
- “遍历数组”
- 与代码完全重复的函数名复述
- 只罗列文件名、不解释因果链

## 新手友好标准

对核心文件，至少满足以下要求：

- 30 秒内能知道该文件负责什么
- 能看懂它属于哪条调用链
- 能区分纯判断逻辑和真实副作用
- 面对长函数时，知道每一段在解决什么问题

如果一段逻辑需要读者在脑中同时记住 3 个以上状态条件，默认应该补注释。
